# barreplay worker

A Cloudflare Worker that hosts the barreplay viewer. Each replay is **one `.brp`
file** in an R2 bucket; the browser reads it directly with HTTP Range requests.
There is **no packer and no per-replay processing** — you upload the `.brp` the
capture tool produced and it plays. Built with [Hono](https://hono.dev) and
[Vite](https://vite.dev) (via
[`@cloudflare/vite-plugin`](https://developers.cloudflare.com/workers/vite-plugin/));
the viewer is plain Canvas/vanilla-JS (no framework).

## How it works

A `.brp` is a container: `"BRP1" <ver>` then tagged sections `M`(meta) `F`(frames)
`X`(economy) `E`(events), each `<tag><len u32le><payload>` (see `snapshot/brp.go`).
Frames and economy are split into independently-gzipped **chunks** (~1 min each),
indexed by byte range in the meta block. So the browser can:

1. Range-read the small `M` block at the front → build the head (teams, unit types,
   icons, bounds, chunk index) entirely client-side, and the `E` block → events.
2. Range-read each frame chunk from the `F` section on demand (and its economy from
   the parallel `X` section), decoding it in the browser with `DecompressionStream`.

The Worker (`src/worker/index.ts`) is thin: it lists the bucket's `*.brp` for the
picker (`/index.json`) and streams a `.brp` with Range support
(`/replays/<id>.brp`). It never decodes a frame. The SPA, unit icons (`/icons/*`),
rank icons (`/ranks/*`) and the icon table (`/icontypes.json`) are fixed static
assets. Map terrain is fetched browser-side straight from `api.bar-rts.com`.

## Uploading a replay

Each replay is a single object at bucket key `<id>.brp`. Upload the `.brp` the
capture produced — that's the whole flow:

```sh
# once: create the bucket + log in to the account in wrangler.jsonc (account_id)
npx wrangler r2 bucket create barreplay-replays
npx wrangler login

# upload one replay to REAL R2 (note --remote; wrangler defaults to local!)
npx wrangler r2 object put barreplay-replays/<id>.brp --remote --file <id>.brp
```

It appears in the picker immediately (the listing is built live from the bucket).
For many replays, `rclone`/`aws s3` against R2's S3 API works too (needs an R2 API
token). There is no `index.json`, no `.brw`/`.resources`, and no chunk files to
manage.

## Layout

```
worker/
  wrangler.jsonc          Worker config (name, main, account_id, assets + R2 binding)
  vite.config.ts          Vite + @cloudflare/vite-plugin
  index.html              viewer page (Vite entry)
  public/app.js           viewer (reads the .brp over Range, decodes in-browser)
  public/style.css
  public/icontypes.json   icon table (name -> {p,s}); generated from Go, committed
  public/icons, ranks/    synced from internal/viz/bardata by tools/sync-assets.mjs (gitignored)
  src/worker/index.ts     Hono app: list *.brp + stream a .brp with Range
  tools/sync-assets.mjs   copies icons and regenerates icontypes.json before dev/build
```

## Commands

```sh
npm install
npm run dev         # vite dev — runs the Worker in workerd + HMR (needs a local R2, see below)
npm run build       # sync assets, build client + Worker into dist/
npm run preview     # preview the production build
npm run typecheck   # tsc --noEmit
npm run cf-typegen  # regenerate worker-configuration.d.ts from wrangler.jsonc
npm run deploy      # build, then wrangler deploy (needs Cloudflare auth)
```

For local dev, seed the local simulator's R2 (wrangler dev binds the
`preview_bucket_name`):

```sh
npx wrangler r2 object put barreplay-replays-preview/<id>.brp --local --file <id>.brp
npm run dev
```

`public/icontypes.json` is committed and regenerated by `sync-assets` when Go is
available (`go run ./cmd/barreplay-icons`); it changes only when the vendored icon
set does.

## Alternative: public R2 domain

Instead of the Worker proxying R2, you can expose the bucket on a public R2 custom
domain (it serves Range natively + CDN-caches) and point the viewer's fetch base at
it — then the Worker only serves the SPA. The pass-through route is used here so the
project is self-contained and testable.
